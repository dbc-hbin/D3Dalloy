### 1. No demonstrated queue/presentation deadlock; same-swapchain HUD motion weighs against it

/Users/hanbinnoh/Documents/dxmt-d3d12/src/d3d12/d3d12_command_queue.cpp:7034-7064 implements D3D12 Wait as a CPU gate on that queue's FIFO worker. It waits for validated producer completion, not merely enqueue. /Users/hanbinnoh/Documents/dxmt-d3d12/src/dxmt/dxmt_fence.cpp:184-234 registers a one-shot completion latch before waiting. /Users/hanbinnoh/Documents/dxmt-d3d12/src/dxmt/dxmt_queue_order.hpp:114-143 makes registration and initial completed-value observation atomic. Thus a stalled compute/scene queue could leave an independent HUD/present queue updating IF the game fails to wait on the stalled result; that requires actual queue topology and dependency evidence, presently absent.

Counterclaim: a Wait stall on the same queue that executes HUD and presents would stop later FIFO tasks too (queue.cpp:805-829). Likewise EncodePresent waits the preceding frame ID before allocating a drawable (queue.cpp:7215-7227), and native retirement only presents completed/current-epoch frames (queue.cpp:661-690). These mechanisms operate on the entire drawable, not selectively on scene pixels. A persistent full present stall cannot by itself explain genuinely changing game HUD pixels in the same swapchain. A separate overlay/window is an alternative; the user's observation does not establish swapchain identity.

### 3. Temporal history ordering and completion ownership are explicit, not an obvious stranded-event bug

queue.cpp:6437-6475 commits application prefix, creates the temporal segment, retains OwnedTemporalFrame in the inflight owner, enqueues history waits, encodes, commits/signals its history timeline, then starts the following application segment. /Users/hanbinnoh/Documents/dxmt-d3d12/src/d3d12/d3d12_temporal.cpp:229-243 holds the feature mutex, waits preceding sequence, increments sequence, derives effective reset, encodes and ALWAYS commits/signals even on encode error. Encode failure removes the whole device, rather than silently continuing fresh HUD presents. The next generation resets after an encode failure.

The device temporal submission mutex is acquired after ring reservation (queue.cpp:4730-4731), held through segment commit, and released before next segment reservation. It serializes CPU encode/commit of entire temporal-containing Execute tasks' segments, including application work within them. It is not held across a GPU completion or ring-capacity wait. This avoids opposite-feature lock inversion but potentially reduces CPU parallelism. Its performance cost is unmeasured.

Native MetalFX segmentation is separate from D3D12 segmentation: /Users/hanbinnoh/Documents/dxmt-d3d12/src/winemetal/unix/metalfx-backend.mm:2113-2157 creates prefix/scaler/suffix native buffers, with optional additional alpha scaler segment, and explicit device-visibility queue barriers. /Users/hanbinnoh/Documents/dxmt-d3d12/src/winemetal/unix/winemetal_metal4.c:133-148 retains all segments under one recording; :521-523 flattens them in recorded order into one native commit, preserving recording/allocator leases. :494-499 releases leases only after BOTH native feedback and commit return, then reports completion. Hence no evidence that only the first MetalFX subsegment retires or that resources are released before the scaler finishes.

Static calculation, not measured frame counts: one Execute task containing exactly one temporal encoder and no other segmentation submits three logical queue submissions (prefix + temporal + suffix). Its temporal submission contains three native command buffers, or four with alpha scaling. Thus Execute uses five native buffers, or six with alpha, before any separate Present/Signal. Every separate Present and Signal adds a submission. Empty prefixes/suffixes are still committed. Removing these blindly is unsafe because history wait placement and producer visibility motivated these boundaries.

### 4. Completion/ring blocking is whole-queue backpressure, not selective frozen-scene behavior

queue.cpp:618-633 retires submissions in sequence and waits each native grouped submission. :731-737 destroys inflight leases and retires the ring BEFORE publishing public fence completion. /Users/hanbinnoh/Documents/dxmt-d3d12/src/d3d12/owned_submission_ring.hpp:24-31 blocks reserve when published minus retired reaches capacity; capacity is 32 at queue.cpp:55. A missing native feedback would therefore stop that queue after 32 outstanding logical submissions, preventing continuing same-queue HUD/presents. This is a bounded static implication, not evidence of a missing callback in this run. Native feedback absence would require a stack/trace and per-queue outstanding sequence capture.
