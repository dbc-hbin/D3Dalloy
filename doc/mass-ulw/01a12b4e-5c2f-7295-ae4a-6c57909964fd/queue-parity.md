## Queue/presentation parity result

No new independently actionable D3DMetal parity gap was confirmed in this domain. The source contains the submission planner, nonconsecutive render-pass grouping, resource/stage frontiers, pending-clear batching, simple-indirect bypass, and retained visibility intervals that an inventory-only comparison could incorrectly call absent.

### Confirmed difference: commit-time native Present reservation

**Reference body and offset.** `D3DMCommandQueueWorker::DoPresent` at `0x1556a4`, full Evidence ID `ev_e9a9c24ebb545a3fd0a7cd624320f0e9ea3a15980174edde5c9aecd571683bc0`, was read. Its MTL3 branch calls `presentDrawable:` or `presentDrawable:afterMinimumDuration:` before command-buffer `commit`. Its MTL4 branch commits the present command buffer, signals the ordering event and drawable, then calls drawable `present` or `presentAfterMinimumDuration:` directly from the worker. The completion/feedback handlers are installed for retirement, not as a prerequisite to the native Present call. `DXGISwapChain::Present1`, `0x114d70`, derives duration from SyncInterval/display rate or the FPS limit and forwards into this queue path; Evidence `ev_e8073a15e38fb1bcb77a1f1596de293504fca48e5a7bd1185df8dad0016eb46d`.

**Exact owned counterpart.** `src/d3d12/d3d12_command_queue.cpp:8284-8302` captures `native_present` for completion-time delivery; `CommandBufferWaitingThread` waits for completion at `896-900` and calls `WMT4::PresentMetal4Drawable` only after successful completion and a current restart epoch at `930-939`. `CommittingScope::~CommittingScope`, `1052-1065`, commits and signals event/drawable but does not submit native Present. The wrapper at `src/winemetal/Metal4FX.hpp:8-13` accepts duration/composition/cadence/tearing, not an epoch-conditional native reservation or cancellation handle.

**Game-path relevance.** This is on the normal D3D12 HWND Present route, not a diagnostic-only method: owned `d3d12_swapchain.cpp` Present1 computes cadence and calls the current backbuffer's Present queue; that queue encodes and retires through the bodies above. It can affect when a ready game frame is offered to Core Animation. No current game trace, latency delta, FPS gain, or frame-time improvement was measured, so those remain hypotheses rather than results.

**Minimal independent recommendation.** Do not move the native Present call earlier under the existing contract. The owned implementation deliberately suppresses both a stale in-flight RESTART frame and a failed GPU submission; reference DoPresent does not show an equivalent epoch gate. First establish a native reservation contract that can cancel an already reserved drawable or conditionally deliver it against the epoch and GPU result. Only then replace completion-time delivery with commit-time reservation, retaining exactly-once credit/observer retirement. If the native contract cannot provide those guarantees, retain current behavior. This is the exact blocker already recorded in PRIORITIES, not implementation work newly authorized by this comparison.

**Focused validation command after such an implementation:**

```sh
python3 scripts/test-owned-graphics.py --runtime "$RUNTIME" --fixture "$PRESENT_QUEUES_FIXTURE" --suite present-queues --mode present --validation --out "$OUT"
```

Use an actual staged runtime and matching built fixture; this is a recommended command, not an executed one. The generic runner's architecture gate must not be weakened to run FEX. Existing `graphics-translator/tests/owned-d3d12-present-queues.cpp:546-634` covers the already-committed frame discarded by RESTART and native decision evidence, with adjacent queue-credit/removal cases. A change needs explicit GPU-error suppression evidence as well. The existing fixture contains timing-based encoding/handler assumptions (`571-572`, `595+`); a new proof should subscribe to the exact encode/commit/retirement state before triggering RESTART rather than treating a fixed wait as proof that the native frame was committed.
