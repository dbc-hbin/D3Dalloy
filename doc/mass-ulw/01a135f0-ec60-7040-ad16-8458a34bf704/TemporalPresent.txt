I read this as a read-only bottleneck hunt through the temporal/FG/present path — I'll report ranked candidates with cited triggers. Stop condition: all scoped paths dispositioned and each candidate cited.

## Summary

The temporal/FG path is not obviously GPU-bound. The strongest avoidable costs are (a) two independent CPU→GPU completion gates on the present path that cap how far the CPU can run ahead of the GPU, and (b) per-frame host-side churn in the native FG/SR backends (transient texture allocation, residency-set re-commit, a redundant full-frame blit). Nothing here contradicts "P1 depth-only pass moved nothing": a GPU pass only helps FPS if the frame pipeline is not pinned by these gates. All magnitude statements below are inferred; only code behavior is confirmed.

## 2. Candidates

**C1 — Reflex low-latency Sleep is a full CPU↔GPU completion gate on the game thread.** `src/d3d12/d3d12_reflex.hpp:92-108`, called at `src/d3d12/d3d12_command_queue.cpp:8330`. Chain: game calls `Present` → `reflex.Sleep(true, do_not_wait)` → `gpu_busy = low_latency_ && pending_ != 0` → `cv_.wait` until `pending_ == 0`. `pending_` counts submitted command buffers *and* presents (incremented by `Capture` at d3d12_command_queue.cpp:7785 and 8359, decremented only in `Work::~Work` at d3d12_reflex.hpp:46-47, i.e. at GPU completion). So Present returns only after the previous frame's GPU work — including its present-carrying submission — has completed. Activation: any game calling `NvAPI_D3D_SetSleepMode` with low latency (nvapi.cpp:737-757), i.e. essentially every Reflex/DLSS-FG title. Classification: CPU gate, steady. Confidence: high on mechanism, medium on being the limiter (unmeasured). Counterevidence: the in-code comment admits it is a completion gate standing in for a predictive model (d3d12_reflex.hpp:101); bounding queue depth to 1 is the intended Reflex behavior. Remedy: admit while `pending_ <= 1` instead of `pending_ == 0` (or drive the deadline from the previous GPU span) — one-line condition change at d3d12_reflex.hpp:102. Falsifier: log Sleep duration per frame and compare frame time with `SetSleepMode(0,0)` from a test harness; if Sleep ≈ GPU span and FPS jumps when low-latency is off, the gate is the limiter.

**C2 — Present encoding waits on the previous present's GPU completion.** `src/d3d12/d3d12_command_queue.cpp:8204-8208` (`while (!order_event.waitUntilSignaledValue(frame_id - 1, 100))`), with the event signaled at 8289-8290. Chain: queue worker `EncodePresent` → spin/wait for `present_order_event_` value `frame_id-1` → only then `StartCommitting`, `nextDrawable`, encode. The predecessor's value is signaled when its command buffer completes on the GPU. Activation: always (every swapchain present). Classification: CPU gate, steady. Confidence: high on mechanism; the loop is only entered when the predecessor is unfinished, so cost depends on how far the GPU trails. Counterevidence: this is what keeps cross-queue present order correct and prevents unbounded drawable pooling; the 100 ms timeout bounds a stall. Remedy: gate on *encoding* order (a CPU-side counter) and let the GPU event ordering handle the queue, or let the worker encode one frame ahead and only block the drawable acquisition. Falsifier: trace the wait-loop iteration count per frame (`present_native_decision` trace already exists); if iterations > 0 in steady state, the CPU is one frame behind the GPU.

**C3 — FG allocates 5-8 new textures plus buffers, views and two residency sets per frame.** `src/winemetal/unix/metalfx_frame_generation.mm:804-819` (current/ui/normalizedDepth/normalizedMotion/output, all `newTextureWithDescriptor`), `:960-980` (parameter buffers via `newBufferWithBytes`, `:585-589`), `:1360-1367` (depth/motion per Prepare), `:685-703` (a brand-new residency set with `addAllocation` for every object + `commit` + `requestResidency`, per encode — twice per frame). At display resolution RGBA16Float this is ~66 MB per output-sized texture allocated and freed every generated frame. Activation: DLSS-FG (`GenerateFrames`) with the feature configured on. Classification: CPU + memory, steady. Confidence: high that the allocations happen; medium on cost magnitude (Metal's allocator recycles, so the real cost is host time per allocation and any heap growth when the GPU lags). Counterevidence: `ExecutionLease` retains objects only until GPU completion, and the interpolator's textures are private/untracked; RR and SR both prove pooling is feasible (metalfx_rr.inc:210-263, metalfx-backend.mm:408-500). Remedy: hold the per-frame intermediates in the `Configuration` object and reuse them when the key (formats + output size + directDepth/directMotion) matches, exactly as `dxmtRRResources` does. Falsifier: count `newTextureWithDescriptor`/`newResidencySetWithDescriptor` calls per frame (Instruments Allocations or a counter around `privateTexture`) — expected 5-8 textures and 2 sets per frame today.

**C4 — FG copies the full present frame into the output before every generated frame, then overwrites it.** `src/winemetal/unix/metalfx_frame_generation.mm:960-980` builds `copies[0] = {present, output, present.width, present.height}` and encodes it; the scatter kernel then writes the entire extent unconditionally (`fsr-kernels.metal:335-379`, `dispatchThreads` extent = `configuration.outputWidth/Height`, metalfx_frame_generation.mm:876-884). The NGX frontend always passes a full-display generation rect and `output_subrect_only = 0` in the normal path (nvngx_d3d12.cpp:899-931). Activation: FG generate; the copy is redundant whenever the scatter covers the full output. Classification: GPU bandwidth, steady, display-resolution (≈66 MB of traffic per generated frame at 4K BGRA8). Confidence: high on redundancy, medium on it being visible (blits overlap with other work). Counterevidence: the copy may be load-bearing for the `disableHint`/reset path where the scatter's result should not seed display, and for `real_output` (that copy at `:969` is semantically required). Remedy: skip `copies[0]` when `!d.output_subrect_only` and the dispatch extent equals the output rect. Falsifier: delete the copy under that condition and compare GPU bandwidth counters/frame time; unchanged time means it was fully overlapped.

**C5 — SR re-commits its residency set (22 allocations) every frame; FG never reuses one.** `src/winemetal/unix/metalfx-backend.mm:1282-1283` (`takeBundle` keyed on `PreparedFrame::Impl*`, so a per-frame-prepared frame never matches, metalfx-backend.mm:562-570) → `takeResidency()` → `makeResidencySet(..., reusable)` re-runs up to 22 `addAllocation` plus `commit` per frame (metalfx-backend.mm:243-284), with an O(n²) duplicate scan. The old set is only returned to the pool after `removeAllAllocations` + `commit` (metalfx-backend.mm:285-297). Activation: every SR frame from NGX/FSR3. Classification: CPU host round-trips, steady. Confidence: high on the code path; medium on magnitude (each `WMTMetal4Call`/Metal call is a Wine unixcall round trip, so tens of calls per frame are real but likely tens of microseconds). Remedy: key the cached bundle on the binding tuple rather than the frame pointer (the frame is new every frame by construction), or keep a per-binding-signature committed set. Falsifier: count `addAllocation`/`commit` per frame and time the native `prepare` call; if native prepare is a meaningful fraction of the frame's CPU, this is a target.

**C6 — Changing output extent destroys the whole native temporal feature, including all cached generations and pools.** `src/d3d12/d3d12_temporal.cpp:162-177`: when `create.DynamicOutputEnabled && (ow != feature_output_width || oh != feature_output_height)`, a new `TemporalFeature` is created synchronously on the game thread and the old one is `markDormant()`ed, which releases scratch textures, buffers, bundles, residencies and all 8 scaler generations (metalfx-backend.mm:619-641, 1889-1891). Activation: `src/fsr/fsr.cpp:284` sets `DynamicOutputEnabled = TRUE` for the FSR3 path, and FSR3 games pass per-frame `upscaleSize` (fsr.cpp:200-201), so any dynamic-resolution step or output-size change triggers it; the NGX path leaves the flag false. Classification: CPU/startup-style hitch, per size change (plus pool-refill frames afterwards). Confidence: high on the trigger; medium on frequency in the reported scene. Remedy: let the existing `ensureScaler`/generation cache handle output-size variation (it already keys on output width/height and caches 8 generations) instead of recreating the feature — or gate the recreation to a hysteresis band. Falsifier: trace `CreateOwnedTemporalState`-style recreation events (add a counter next to the `temporal_record` trace) and correlate with frame-time spikes while changing resolution scale in-game.

**C7 (supporting) — SR's display-resolution output tail does not shrink with the game's render passes.** When transfer, sharpening, capped output or alpha is active, SR allocates a private output shadow at temporal (display) resolution, runs an FSR finish compute pass and a full-frame copy (`metalfx-backend.mm:1286-1296`, `1992-1998`, `1741-1772`). Activation: FSR3 sharpening/sRGB/PQ paths (fsr.cpp:202-208, 205). Classification: GPU, steady, resolution-scaling-relevant. Confidence: medium. Remedy: none cheap; measure before touching. Falsifier: compare frame time with sharpening disabled.
