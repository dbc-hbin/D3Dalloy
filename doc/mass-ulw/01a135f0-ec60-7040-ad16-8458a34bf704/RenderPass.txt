## 2. Candidates

### C1 - The P1 depth-only fix cannot move GPU time; the planner already merges those passes
*Chain:* app calls `OMSetRenderTargets(0,nullptr,dsv)` → 7337 elides the rebind (pre-fix: `EndSchedulingPass` 7437 closed the encoder) → pre-fix the split produced two `RenderEncoderData` with identical attachments → queue planner 5725-5815 merges them anyway (`AppendRenderMember` 318-320 accepts an equal depth/stencil view whose load actions are `Load`; `OrdinaryRenderRejection` 137-170 passes: endpoint reason is `Scheduling`, not `Opaque`, `submission_group_safe` true, attachments Load/Store) → **one native pass either way**. What the fix actually saves is recording-side: one `EncoderData`, its CPU-heap command nodes, and the 8-bit dirty-state reset (2415-2418) that forces the next draw to re-emit fixed state.
*Activation:* every depth-only rebind; saving scales with how often the title re-binds (once per pass ≈ nothing; per draw ≈ real CPU).
*Class:* CPU/recording, steady. *Confidence:* high that GPU pass count is unchanged; medium on the size of the CPU saving.
*Counterevidence/existing opt:* the merge path itself (5725-5815) is the existing optimization that makes the fix GPU-neutral.
*Minimum safe remedy:* none - keep the fix, stop attributing FPS to it.
*Falsification:* count queue `native_render_begin` (6833) per frame with and without the fix. Unchanged ⇒ no GPU delta. Count recording `pass_end` with `function == "OMSetRenderTargets"` (allocator 201-203) to size the CPU delta. If `pass_end` collapses but `native_render_begin` does not, the FPS ceiling is elsewhere - which is what your measurement shows.

### C2 - Render-pass ending-access DISCARD never becomes a no-store (GPU bandwidth)
*Chain:* `BeginRenderPass` 10111-10225 binds through `OMSetRenderTargets` (load=`Load`, store=`Store`, 2324-2353), issues beginning CLEARs (10199-10216), and records only RESOLVE ending accesses (10166-10176). `DISCARD` and `PRESERVE_LOCAL_*` (constants 10051-10052) never touch `store_action`; `EndRenderPass` 10234-10263 only resolves and unbinds. `DiscardResource` is an explicit no-op (7903-7909). Grep: `WMTStoreActionDontCare` appears only in `src/dxmt/dxmt_context.cpp:1355-1358`, never in `src/d3d12`.
*Activation:* any title using `BeginRenderPass` with `ENDING_ACCESS_TYPE_DISCARD` (typical for shadow/depth-only and scratch RTs) or `DiscardResource`. *Class:* GPU steady-state, TBDR tile store per attachment per pass.
*Confidence:* high on the code fact; medium on magnitude (Metal may already elide untouched tiles - needs a GPU trace).
*Existing opt/counterevidence:* beginning-access DISCARD correctly needs no work (10045-10048); a later *clear* already becomes a load-action clear, so only the store side is missing.
*Minimum safe remedy:* in `BeginRenderPass`, set `store_action = WMTStoreActionDontCare` for attachments whose ending access is DISCARD (leave PRESERVE_LOCAL_* at `Store`, since the emulation's "local" guarantee currently rides on that store). This also requires relaxing the two consumers that hard-require `Store` - `OrdinaryRenderRejection` (queue 152-155) and the rebind-elision check (7354) - otherwise a discarded pass becomes unmergeable, trading a store for a whole pass. A merged group inherits the first member's store action (queue 296-297, 304-317), so take DontCare only when the group's *last* member discards.
*Falsification:* Metal System Trace / bytes-written counter for one frame with and without the mapping; expect a drop proportional to discarded attachment bytes × passes. If flat, Metal was already eliding.

### C3 - Resolves never fold into the producing pass (one extra full-attachment load+store per resolve)
*Chain:* `EndRenderPass` 10246-10252 → `ResolveSubresourceRegion` → `ResolveTextureRegion` 9455-9600 → `allocator_->InvalidateCurrentPass(); AllocatePass<ResolveEncoderData>()` (9580-9585). Queue 7464-7528 encodes it as its own render pass; for a color MSAA resolve 7497-7501 sets source `load_action = Load`, `store_action = StoreAndMultisampleResolve` - the MSAA source is loaded from memory (full tile load of a 4x/8x surface), stored again, plus the destination store.
*Evidence the fold is intended:* `RenderEncoderColorAttachmentData::resolve_attachment` exists (encoder hpp 157) and the queue consumes it (6727-6730), but **nothing in `src/d3d12` ever writes it** (grep: reads only at 7352, queue 152/6615/6800). The D3D11 backend performs exactly this fold at `dxmt_context.cpp:1360-1374`.
*Activation:* any `ResolveSubresource` per frame (MSAA resolve, post-process downsample, min/max, decompress) and every render-pass ending-access RESOLVE. *Class:* GPU steady.
*Confidence:* high that an extra native pass is emitted; high that the mechanism is available (d3d11 proves it); medium on the FPS share without knowing the title's resolve count.
*Minimum safe remedy:* in `ResolveTextureRegion`, if the last encoder is a `Render` whose color attachment is the resolve source at the same level/slice/format with `Load`/`Store` actions, set that attachment's `store_action = StoreAndMultisampleResolve` and `resolve_attachment = dst` instead of allocating a Resolve encoder (mirror `dxmt_context.cpp:1360-1374`). Note the existing guard at 7352 deliberately blocks *re-merging* a resolve-bearing pass - keep that.
*Falsification:* count `native_render_begin` events labelled `ResolvePass` (queue 7512) per frame; after the fold it must be zero and total native passes must drop by the resolve count.

### C4 - The 64-buffer budget is a merging cliff; under native MSAA it splits mid-recording into Opaque (unmergeable) pieces
*Chain:* draw → `PreDraw` 2448 `CaptureSubmissionAccess` (1882-1966) → at 64 entries 2460-2461 sets `submission_snapshot_budget` and clears `submission_group_safe` → queue 139 `"recorded_buffer_budget"` → `access_complete = false` (5402) → no merging (5725) and `history.clear(); partition = index+1` (5817-5819) resets the merge window for later nodes. Under native MSAA the same budget is re-checked in `PreDraw` 2224-2236 and **invalidates the pass** (2235, `InvalidateCurrentPass`, not `EndSchedulingPass`) → `endpoint_reason` stays `Opaque` → queue 141 rejects every piece, so each becomes its own native pass with fences (6869, 7004).
*Activation:* any ordinary render encoder touching >64 distinct buffer ranges - roughly 20-30 draws with distinct vertex buffers plus root descriptors, i.e. most city-scene passes; native-MSAA titles hit the mid-recording split repeatedly. *Class:* GPU (extra passes) + CPU (merge window reset).
*Confidence:* mechanism high; hit-rate for this title unknown (the login screen's ~30 draws would not hit it).
*Minimum safe remedy:* keep the buffer list capped but stop clearing `submission_group_safe`/`submission_snapshot_budget` on budget - the budget exists to bound the access list, not to invalidate replay; and for native MSAA replace `InvalidateCurrentPass` with `EndSchedulingPass` so the pieces stay `Scheduling` and mergeable.
*Falsification:* count `submission_render_rejected` with reason `recorded_buffer_budget` (queue 5801-5807) and `native_msaa_budget_rollover` (2232-2234) per frame. ~0 ⇒ C4 is not your bottleneck.

### C5 - Every ordering barrier is a native pass boundary, including COMMON transitions
*Chain:* `ResourceBarrier` 6471-6488 sets `needs_boundary` for UAV/aliasing barriers, split flags, and any transition whose before/after is COMMON or includes a write state → `EndSchedulingPass` 6486 → the next draw opens a new render encoder → the planner sees `boundary_before` on the following node (queue 5520) → no merging → a separate pass with `updateFence`/`endEncoding` (7004) and `waitForFence` (6869). Enhanced `Barrier` splits on any `SyncBefore`/`SyncAfter` ordering (6589-6592, 6798-6801).
*Activation:* every RT→SRV→RT chain and every COMMON-state resource touched per frame. *Class:* GPU steady; count scales with barriers per frame. *Confidence:* mechanism certain; avoidability medium - most of these boundaries are legitimately required because resources use untracked Metal storage (comment 6425-6432).
*Existing opt:* read→read transitions without COMMON are exempt (6482-6484); a scheduling split can still be merged by the planner.
*Minimum safe remedy (only if measured to matter):* use the state-event tracker (6474-6480) to skip the boundary when `StateBefore == COMMON` and no prior write to that subresource was recorded in this list - a proof-based exemption, never a blanket one.
*Falsification:* count `pass_end` with `function == "ResourceBarrier"/"Barrier"` and `native_render_begin` per frame; correlate with FPS over a barrier-heavy frame section.

### C6 - Per-draw submission-access capture is O(parameters × bindings) with linear dedup
*Chain:* `DrawInstanced` → `PreDraw` 2448 → 1882-1966: for each root parameter, for each pipeline resource binding, `ForEachUsedDescriptorRange` plus two `std::none_of` scans over up to 64 recorded entries (1920-1928), then the 32-slot vertex-buffer loop (2451-2465). Per draw, on the recording thread. *Class:* CPU/recording, steady. *Confidence:* high on structure; share unknown.
*Minimum safe remedy:* reuse the planner's address-keyed map (`access_slots`, queue 86) or a small sorted vector instead of the linear scans.
*Falsification:* the `complete` trace reports `cpu_submit_ns` per submission (queue 926) - compare CPU time per frame with the capture short-circuited by an env toggle; if GPU-busy is the ceiling, C6 is irrelevant.
