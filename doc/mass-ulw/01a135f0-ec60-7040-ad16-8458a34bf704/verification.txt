### Depth-only `OMSetRenderTargets` and native pass count

The precise answer is **yes, it can affect native pass count, but not universally**.

- The depth-only reuse path can keep the current recorded render encoder when the DSV and dimensions match: `src/d3d12/d3d12_command_list.cpp:7337-7349,7388-7410`.
- The old non-reuse path calls `EndSchedulingPass`, which marks and invalidates the current encoder: `src/d3d12/d3d12_command_list.cpp:7425-7442`; `src/d3d12/d3d12_command_allocator.hpp:198-216`.
- Separate eligible render nodes can later be merged into one `RenderReplayGroup`, and the native encoder is opened once with a `members` count: `src/d3d12/d3d12_command_queue.cpp:5730-5814,6832-6835`.

Therefore:

- If the old depth-only boundary produced two nodes that the submission planner can merge, the native pass count was already one; P1 changes recorded `pass_end`/planning work but not `native_render_begin`.
- If the boundary caused a node to become unmergeable, or the node was already rejected by access/state conditions, avoiding that boundary can reduce `native_render_begin` and therefore can have a GPU-visible benefit.
- The correct trace test is `pass_end` versus `submission_render_merged` versus `native_render_begin`, not pass/draw counts from an unrelated login trace.

- “The depth-only fix cannot affect GPU/native pass count” is too strong.
- “Fence update covers all render stages” is false for ordinary renders; the default update is Fragment.
- “Root/vertex tables are set every draw” is unsupported; dirty-state and native-value caches suppress unchanged updates.
- “NaN lowering costs every shader” is unsupported; it applies to lowered sample operands.
- “Null descriptors use per-lane branches” is unsupported; null guarding is operation-level.
- “SR/FG completion is only a completion-thread gate” is stale; Metal4 reservation tickets, commit-return drawable signaling, feedback, and retirement all participate.
