## Candidates

### C1 — One shared MTLFence serializes every consecutive render pass
`src/d3d12/d3d12_command_queue.cpp:6869` (`encoder.waitForFence(fence_, wait_stages)`) and `:7004` (`encoder.updateFence(fence_, update_stages)`); rejection gate at `:5401`.

**Chain:** `ProcessExecute` → per `EncoderType::Render` encoder → one queue-wide `WMT::Fence fence_` (declared `:600`, created `:1278`). Pass N ends by updating the fence after `update_stages`; pass N+1 begins by waiting before `wait_stages`. A single MTLFence carries one monotonic value, so pass N+1's waited stages cannot start until pass N's update executes. When `replay_current_node->access_complete` is false, `wait_stages` is the conservative `Vertex` (or `PreRaster`) and `update_stages` the `Vertex|Fragment|Object|Mesh` union (`:6996–7003`); when true, both narrow to the proven hazard stages (`:6860–6869`).

**Activation:** every submission; severity depends on how many passes are `access_complete`. `OrdinaryRenderRejection` (`:123–160`) rejects on `dsv_readonly_flags` (read-only DSV — standard for the main opaque pass), `default_raster_sample_count` (MSAA), `dsv_readonly_flags`, `render_target_array_length > 1`, and others. `fenced` (`:5270`) rejects **all** render and compute nodes in the submission when any list encodes a `WaitBarrier`/`SignalBarrier`.

**Class:** GPU / steady state (lost overlap). **Confidence:** confirmed code behavior; **inferred** performance impact.

**Counterevidence:** grouped members share one native render encoder (`:6902–6921`), so no fence sits between merged passes. The P1 depth-only grouping fix produced negligible FPS gain — which either means those passes were not eligible (`fenced`, MSAA, read-only DSV, `ReservedResource::AnyLive()`), or that pass-to-pass serialization is not the limiter. Also, in a sequential deferred renderer most consecutive pass pairs have a genuine fragment→vertex hazard, so the fence may cost nothing beyond the real dependency.

**Minimum safe remedy:** narrow `wait_stages`/`update_stages` for non-`access_complete` passes from the conservative union to the stages actually produced/consumed (a per-pass `wmtcmd`-derived stage set), and, for independent attachment sets, drop the fence update/wait pair entirely when the plan proves no cross-pass access overlap.

**Falsification:** with `OWNED_GRAPHICS_TRACE=1 OWNED_GRAPHICS_TRACE_LIMIT=200000`, per frame count `submission_render_candidate` events by `eligible`/`reason`; compute GPU idle as `gpu_start_ns(submission N+1) − gpu_end_ns(submission N)` from `complete` events. If consecutive-pass gaps are already ≈0, C1 is dead.

### C2 — Default-on DRED breadcrumbs walk every draw on the app thread
`src/d3d12/d3d12_command_queue.cpp:7830–7884` builds `std::vector<D3D12_AUTO_BREADCRUMB_OP> history` by walking every encoder's `cmd_head`→`next` chain (one `push_back` per draw/dispatch/copy/clear/resolve/barrier) plus a `std::string` per diagnostic annotation; `:7885` calls `BeginSubmission`.

**Chain:** `ID3D12CommandQueue::ExecuteCommandLists` (`:7772`) holds `mutex_enqueue_` (`:7784`) across the whole walk, then `DeviceDiagnostics::BeginSubmission` (`d3d12_diagnostics.cpp:420–467`) takes a device-global `recursive_mutex`, `make_shared`s a breadcrumb, resolves list and queue debug names via two `GetPrivateData` calls, moves the history in, linear-scans up to 128 retained entries, and pushes. `capture_enabled` is true by default (`:405`), so the early return at `:422` does **not** skip the walk.

**Activation:** every `ExecuteCommandLists`, on the application thread. **Class:** CPU / steady state. **Confidence:** confirmed code; magnitude inferred (proportional to commands submitted per frame).

**Counterevidence:** none in-tree; the 128-entry bound and the `contexts` reservation are already deliberate trims. The `trace`/diagnostics fields are needed for DRED correctness, and `Complete` only sets an integer.

**Minimum safe remedy:** hoist the eligibility check — expose `DeviceDiagnostics::BreadcrumbsEnabled()` and skip history construction entirely when false, and/or build `history` only on the fault path from the recorded command stream.

**Falsification:** time `ExecuteCommandLists` (or `BeginSubmission`) with breadcrumbs forced off vs. on for one fixed frame; if the delta is ≪1 % of frame time, C2 is dead.

### C3 — Per-`ExecuteCommandLists` SubmissionPlan construction on the single submitter
`src/d3d12/d3d12_command_queue.cpp:5459` (`plan.nodes.push_back`), node shape at `:80–91`, anchors map at `:5378`/`:5458`, barrier maps at `:5277` and `:7897`.

**Chain:** `SubmissionThread` → `ProcessExecute` → `validate_transitions` builds a fresh `unordered_map<BarrierTracker*, BarrierResourceState>` (deep-copying persistent tracker state per distinct resource) → node loop constructs one `SubmissionNode` (one `unordered_map` + four vectors) per encoder and grows `plan.nodes` without reserve → group matching runs `AppendRenderMember` trials over prior candidates. The FIFO worker is the only thread that reaches the GPU, so its per-frame planning time is a hard throughput ceiling: if planning exceeds the frame budget, the GPU starves regardless of GPU-side work.

**Activation:** every `ExecuteCommandLists`; scales with encoders and transitions per submission. **Class:** CPU / steady state (submit-thread throughput). **Confidence:** confirmed code; inferred magnitude.

**Counterevidence:** the `history_checks`/`candidate_checks`/`metadata_copies` counters and `kSubmissionGroupBudget` (`:54`) show this path was already tuned; empty `unordered_map`s allocate lazily, so cost is per distinct resource, not per node.

**Minimum safe remedy:** `plan.nodes.reserve(total encoders)` before the loop, and reuse `SubmissionNode` storage across submissions (a plan object owned by the queue, cleared per call) so the maps/vectors keep capacity; extend the same reuse to `validate_transitions`' `pending` map.

**Falsification:** trace or sample `cpu_submit_ns` minus the previous `complete`'s `cpu_submit_ns` per submission; if worker planning is a small fraction of frame time, C3 is dead.

### C4 — Full native submission object graph per segment, Signal, marker, and Present
`src/d3d12/d3d12_command_queue.cpp:1071` (commit), `:1125–1130` (marker), `:7969–7978` (signal), `:8210` (present); `src/winemetal/unix/winemetal_metal4.c:754–800` (`m4_commit`), `:938–941` (fresh `newCommandBuffer` on every slot reuse), `:736–742` (residency add/remove commit churn), `:283–287` (`addAllocation` per bound resource).

**Chain:** each `CommittingScope` allocates a `DXMTM4Submission`, an `NSCondition`, three `NSMutableArray`s, an `MTL4CommitOptions` with a retained feedback block, a fresh `id<MTL4CommandBuffer>` (because `context->ended`), and performs `[residency commit]` twice per submission. Queue-level `BeginEvent`/`EndEvent`/`SetMarker` each push a `MarkerTask` (`:7953`) which becomes a **complete native submission with no GPU work**.

**Activation:** per segment/`Signal`/marker/`Present`. Marker cost activates only if the application calls queue-level markers (some engines, overlays, and capture tools do; per-draw marking would be catastrophic here). **Class:** CPU + startup/steady GPU queueing overhead. **Confidence:** confirmed code; magnitude inferred.

**Counterevidence:** an empty command buffer is cheap on the GPU; `m4_commit`'s allocations are amortizable by the allocator; the fresh `MTL4CommandBuffer` exists to work around a macOS 27 MetalTools retired-heap bug (comment at `:936–938`), so it is not gratuitous.

**Minimum safe remedy:** batch a `Signal` into the preceding submission of the same queue when one exists (attach `fence_completion` to the last published `InflightCommandBuffer` instead of committing an empty one), and skip the `MarkerTask` submission when the encoder would carry no observable diagnostic (diagnostics disabled).

**Falsification:** count `submit` trace events per frame and classify by whether the submission contained encoders; if signals/markers are ≤2 per frame, C4's submission overhead is negligible.

### C5 — Device-global `residency_lock_` held across every native commit
`src/d3d12/d3d12_device.cpp:2820` inside `CommitMetal4CommandBuffers`; same lock at `:3168` (`LookupBufferByVA`), `:2899`, `:3041`, `:3131`, `:3314`.

**Chain:** every queue's commit takes the device-global `dxmt::mutex`, and the FIFO worker's descriptor resolution takes the same lock per `AppendSubmissionBuffer`. With multiple D3D12 queues (graphics + compute + copy) committing concurrently, all commits serialize, and any long residency mutation blocks commits **and** every VA lookup.

**Activation:** multi-queue workloads, or any frame with concurrent residency register/unregister. **Class:** CPU / steady state (cross-queue serialization). **Confidence:** confirmed code; contention inferred.

**Counterevidence:** the critical section is only `queue.commit(...)` — the comment at `:2816–2819` documents that GPU waits and retirement deliberately run outside it, and critical sections elsewhere are short lookups.

**Minimum safe remedy:** shrink the guarded region to the preCommit allocation traversal it protects, or replace the global mutex with a reader/writer scheme where VA lookups take a shared lock.

**Falsification:** record commit-lock wait time (a one-line `NowNs()` delta around the `lock_guard`) per submission; if p99 wait is under a few µs, C5 is dead.

### C6 — Cross-queue `Wait` is a CPU-blocking gate, not a GPU-side event wait
`src/d3d12/d3d12_command_queue.cpp:8020–8030`; `src/dxmt/dxmt_fence.cpp:191–201` and `:224–226`; `src/dxmt/dxmt_queue_order.hpp:149–201`.

**Chain:** `ProcessWait` blocks the FIFO worker on `FenceCompletionLatch::waitUnless`; the latch fires from the producer queue's completion thread only after GPU retirement. Subsequent tasks on the waiting queue are not submitted at all. `MTL4CommandQueue_waitForEvent` exists in the bridge (`Metal.hpp:1056`) and is used for `timestamp_order_event_`/`alias_flush_event_` but never for D3D12 fences, because D3D12 fences have no per-fence native event — only the shared-memory timeline plus observer threads (`d3d12_fence.cpp:130–150`).

**Activation:** any frame with a cross-queue fence dependency (graphics↔compute ping-pong, async compute, copy-engine handoff). **Class:** CPU latency + lost GPU overlap. **Confidence:** confirmed code; latency cost inferred (~1 CPU wakeup + submission round trip per dependency).

**Counterevidence:** D3D12 semantics already forbid the waiting queue's later work from starting, so the observable ordering is correct; the worker blocking is a *stronger* guarantee than a GPU-side wait, not a weaker one.

**Minimum safe remedy:** give each fence a lazily created `MTL::SharedEvent` and encode the wait on the MTL4 queue (`waitForEvent`/`signalEvent`) so the dependency is resolved in hardware, keeping the CPU latch only for `GetCompletedValue`/`SetEventOnCompletion`.

**Falsification:** trace `wait` events and their timestamps; if the gap between a producer's `complete` and the consumer's next `submit` is under ~20 µs, C6 is dead.
