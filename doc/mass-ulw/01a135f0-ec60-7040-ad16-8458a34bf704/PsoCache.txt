## 2. Candidates

### C1 — Unconditional per-sample NaN clamp in every generated shader (GPU, steady, highest leverage)
- **Evidence (confirmed):** flags set at `d3d12_pipeline_graphics.cpp:1662` (ordinary PS/VS path; `common` is chained via `data_ia_layout.next`/`data_ps.next`), plus `:825,954,2062,2203,2265,2352,2461`; `d3d12_pipeline_compute.cpp:99,203`. Lowering: `src/airconv/nt/air_builder.hpp:627-629` (`select(isnan(x), 0, x)`), applied at `air_builder.cpp:1529-1534, 1633-1638, 1733-1738, 1753-1760` (twice, on both derivatives of `sampleCmp`), `2101-2106, 2189-2194, 2407-2412`. `air_builder.cpp:801-802` applies it unconditionally in the address-mode path regardless of the flag.
- **Caller-to-cost chain:** app `CreatePipelineState` → `MTLD3D12GraphicsPipelineStateImpl::Initialize` → `SM50_SHADER_COMMON_DATA.flags` (`:1662`) → `SM50Compile` → converter → `air_builder` sample lowering → 1-3 extra instructions per texture-sample coordinate in the *final metallib* → GPU cost on every fragment/CS that samples.
- **Activation:** always; no runtime switch.
- **Class:** GPU, sustained (scales with shading rate and sample count), and it also perturbs every stage key (so it is baked into all cached artifacts).
- **Confidence:** code behavior **confirmed**; FPS impact **inferred** — plausibly small per instruction, but it is global, so it is exactly the kind of tax a render-pass/bandwidth fix cannot remove.
- **Existing optimization/counterevidence:** deliberate compatibility decision — `kVersion 7` history says the flag "changes generated shader semantics" (`d3d12_pipeline_cache.cpp:45`); `getNaNToZero` is a plain select and may fold cheaply; the flag is a D3D-conformance choice, not obviously removable.
- **Minimum safe remedy:** none without a conformance decision. Cheapest safe probe: build a variant that omits the flag for pipelines whose PS/CS never samples (e.g. depth-only VS/PS, which is precisely the P1 case), or make the flag a per-PSO decision instead of unconditional.
- **Falsification:** compile one representative PS both ways and diff metallib instruction counts / sample sequences; or measure GPU time on a shader-ALU-bound pass with the flag toggled. If instruction count is unchanged (folded), drop this candidate.

### C2 — `disk_mutex` serializes render-thread blob restores against the publication worker's flushed writes (CPU, stutter + startup)
- **Evidence (confirmed):** reader takes `disk_mutex` around `ReadAutomaticPipelineCache` (`d3d12_pipeline_cache.cpp:1454-1461`); worker holds the same `disk_mutex` across the entire `WriteAutomaticPipelineCache` (`:93-104`), which itself waits up to 1000 ms on a named mutex (`d3d12_shader_cache.cpp:428`), may rescan the directory (`:638-655`), writes up to 64 MB, `FlushFileBuffers` (`:666`) and `MoveFileExW(..., MOVEFILE_WRITE_THROUGH)` (`:669`). The restore then SHA-1s the whole blob (`:1515-1516`) and serialization SHA-1s it again (`:1632-1633`).
- **Caller-to-cost chain:** app `CreatePipelineState` → `cache_.Initialize` → memory miss → `disk_mutex` → file open/read (≤64 MB, `kAutomaticEntryBytes`) → `LoadBlob` → `BlobDigest` (full-blob SHA-1) → `Layout` → `ShareBlob`.
- **Activation:** any PSO creation whose key is not in the 64 MB memory cache, while a publication is in flight; i.e. exactly the mid-gameplay PSO churn that occurs after the live blob set exceeds 64 MB.
- **Class:** CPU (calling thread), stutter; also startup. No steady per-frame cost.
- **Confidence:** code behavior **confirmed**; trigger frequency **inferred** (depends on blob sizes/count — needs the trace counters).
- **Existing optimization/counterevidence:** the design already keeps disk I/O outside the metadata lock, publishes atomically via temp+rename (so concurrent readers of *other* keys need no exclusion), and bounds retention (64 MB/512, `:47-48`). Waiters on the same key join a flight rather than recompile (`:1438`).
- **Minimum safe remedy:** stop taking `disk_mutex` for reads (the write path is already atomic and readers use `FILE_SHARE_*`), or hand the restore to a worker with the flight left pending. No format change.
- **Falsification:** `OWNED_GRAPHICS_TRACE=1` already emits `pipeline_cache_auto_timing` with `phase`/`ns` for `disk_read`, `disk_write`, `metadata_wait` (`:166-181`, `:92-93`). If no `disk_read` overlaps a `disk_write` and `ns` stays in the tens of µs, drop this candidate.

### C3 — Lazy native PSO/shader builds execute inside draw recording (CPU, first-use stutter)
- **Evidence (confirmed):** `GetMSAAPipelineVariants` (`d3d12_pipeline_graphics.cpp:2422-2430`) builds ~6 native PSOs plus up to 4 pixel-shader variants under `msaa_pso_mutex`, reached per MSAA draw from `d3d12_command_list.cpp:3197`. `GetColorWriteMaskPipelineState` (`:2143-2166`) creates a Metal PSO per write-mask combination under `color_write_mask_pso_mutex`, reached on PSO bind (`d3d12_command_list.cpp:2585-2600`). `GetMeshPipeline` (`:2406-2418`) runs `BuildMeshPipeline` (stage compiles + native PSO) under `mesh_pso_mutex`. Also `:2168-2186`, `:2192-2246`, `:2248-2320`.
- **Activation:** first draw needing each variant — statistics/coarse MSAA sets, each write-mask combination, each mesh variant key, index-pull, ICB.
- **Class:** CPU, stutter (single-frame spikes).
- **Confidence:** code **confirmed**; magnitude **inferred** (a Metal PSO link is typically 10-100 ms).
- **Existing optimization/counterevidence:** everything is memoized (`attempted` flags, maps); the two commonest MSAA variants are prebuilt at creation (`:2018`), as are the default mesh variants (`:1954,1959`). Only statistics/coarse/mask/mesh-key permutations remain lazy.
- **Minimum safe remedy:** extend the existing eager warm-up at creation (`:2018`) to the statistics and coarse MSAA variant sets, and to the write-mask combinations the PSO's own RTV mask admits. Moves cost from first draw to creation, where the app already expects to pay.
- **Falsification:** trace `pipeline_artifact_operation` (`kind=native_render`/`native_mesh`, `:509-518`) and check whether any occur between the first `Draw` and frame end during gameplay; correlate with frame spikes.

### C4 — Device-global serialization of native PSO creation (CPU, steady if PSO churn)
- **Evidence (confirmed):** `native_creation_mutex` held across `compiler.newComputePipelineState`/`newRenderPipelineState` (`d3d12_pipeline_cache.cpp:1118-1121`), plus per-PSO mutexes held across the same call (`d3d12_pipeline_graphics.cpp:2164, 2229-2236, 2317, 2406-2418`).
- **Activation:** PSO creation from more than one thread (multi-threaded recording, streaming) — all but one thread waits, for the duration of a Metal link.
- **Class:** CPU, steady during churn.
- **Confidence:** medium-high.
- **Existing optimization/counterevidence:** deliberate — one Metal compile per unique key is exactly the point (the artifact cache dedupes outside the mutex). The mutex only matters because it is held for the compile, not just for bookkeeping.
- **Minimum safe remedy:** none needed if creation is one-time; if C3's remedy is applied, the hold moves off the render thread.
- **Falsification:** two threads creating PSOs concurrently; timestamps of `native_render` operations showing serialization longer than a frame.

### C5 — Second-pass SHA-1 of the whole blob at serialize and restore time (CPU, creation/startup)
- **Evidence (confirmed):** `PipelineCache::Complete` → `GetBlob` (`:1277-1278`) → `BlobDigest` over the full serialized blob (`:1632-1633`); the restore path hashes the same bytes again (`:1515-1516`); stage artifacts SHA-1 the payload on write (`d3d12_shader_cache.cpp:799-803`) and on read (`:706-709`).
- **Activation:** every successful PSO creation (not only misses) and every stage-artifact write/read.
- **Class:** CPU, startup + creation-time.
- **Confidence:** behavior **confirmed**; magnitude **inferred** (SHA-1 at ~1 GB/s ⇒ ~60 ms at the 64 MB cap; typical blobs are far smaller, so tens of µs to a few ms).
- **Existing optimization/counterevidence:** `BlobDigest` skips the digest field to allow a stable fixpoint; the digest is a required integrity contract for the disk cache.
- **Minimum safe remedy:** compute the digest incrementally while the stage bytes are copied in `GetBlob` (single pass instead of a second full pass), or compute it on the publication worker before the write.
- **Falsification:** time `Complete`/`GetBlob` (currently untraced — `pipeline_cache_auto_timing` covers only disk_read/disk_write/metadata_wait). If it is <1 ms per PSO, drop.

### C6 — Silent publication drops under burst (startup, next run)
- **Evidence (confirmed):** `AutomaticCache::Publish` returns when `publications.size() >= 8` (`d3d12_pipeline_cache.cpp:130-137`); `StageArtifactWriter::enqueue` does the same at 8. `Complete` publishes exactly once per key (`:1310-1312`), so a dropped blob is never re-published for that key.
- **Activation:** level-load bursts creating >8 PSOs/stage artifacts faster than the writer drains.
- **Class:** startup cost on the *next* launch (recompiles), not current-frame FPS.
- **Confidence:** high (explicit `return`).
- **Existing optimization/counterevidence:** deliberate bound; the in-memory entry still serves the current run.
- **Minimum safe remedy:** on drain, re-enqueue dropped keys (bounded), or raise the limit to the number of in-flight completions.
- **Falsification:** with trace on, count `pipeline_cache_auto_begin` vs `pipeline_cache_auto_publish` per key across a level load; a gap proves the drop.

## 3. D3DMetal comparison question

Does D3DMetal emit a per-sample NaN-to-zero clamp for D3D sample semantics, or does it rely on Metal's native NaN behaviour for texture coordinates? If D3DMetal does not, then DXMT's unconditional `SM50_SHADER_FLAG_SAMPLE_NAN_TO_ZERO` (`d3d12_pipeline_graphics.cpp:1662` → `air_builder.hpp:627-629`) is a pure per-sample ALU tax that D3DMetal avoids — and its removal would show up as a shading-rate-proportional FPS delta on the same scene, which is exactly the class of cost a depth-only render-pass fix cannot touch.

**Skipped/did not check:** I did not measure anything (no builds/runs), did not read `d3d12_pipeline_library.cpp`'s serialization path in depth (creation-time only, no per-frame role), and did not audit non-PSO per-frame costs (barriers, descriptor heaps, submission), which are the more likely explanation if sustained FPS is low with no PSO churn. **Risk:** C1 and C2 are the only candidates that can plausibly move sustained FPS; both need measurement before acting, and C1's remedy changes shader semantics.
